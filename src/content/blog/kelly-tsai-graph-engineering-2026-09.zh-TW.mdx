## 這篇在講什麼

七月的 AI 圈冒出一個新詞：Graph Engineering。Kelly Tsai 八月中的影片（約 14 分鐘）把這個詞的來龍去脈講得很乾淨，我看完拿自己管一群 AI 的日常對了一遍——連分工是怎麼長出來的過程都一樣。這篇整理影片講了什麼，加上我自己的對照。

## 一個詞怎麼在 48 小時內紅起來

七月十八日，開發者 Peter Steinberger 在 X 上發了一句話：「我們還在聊 loops，還是已經轉向 graphs 了？」一個半小時後，Google 的資深 AI 產品經理接話，給了核心定義：迴圈讓 agent 的行為可以被寫成，圖讓 agent 的組織可以被寫成。48 小時內文章一篇接一篇，有人直接下標「Loop Engineering 已死」。

兩天後 LangChain 創辦人 Harrison Chase 出來吐槽：「我到現在還是不知道 Graph Engineering 是什麼，但這不就是 LangGraph 嗎？」——他做這件事已經三年，GitHub 三萬八千多顆星。狀態機函式庫 XState 的作者更直接：把狀態和轉換定義成有向圖，電腦科學幾十年前就有了。

所以名詞是新的，機制是老的。影片給的判讀我很喜歡：這個詞會紅，本質是一個訊號——大家手上的 agent 已經多到必須當成一個組織來管了。去年沒人需要這個詞，因為去年大家手上都只有一個 agent。

## 兩張圖：一張掛牆上，一張用完就丟

影片說 Graph Engineering 實作起來是同時維護兩張性質完全不同的圖：

組織圖（Graph）像公司的組織圖：手上有哪些 agent、每個管哪一塊、記憶放在哪。它很穩定，可能幾個月才改一次，回答的是「我們有哪些人、誰管什麼」。

分工表（Workgraph）像這一次專案的分工表：任務拆成哪幾個節點、誰先誰後、哪些可以同時做、做完在哪裡合併。它用完就丟，下個專案重畫，回答的是「今天這個案子怎麼分工」。

![左右對照：左邊一張裝框的組織圖，標著穩定、幾個月改一次；右邊一張分工表草稿，發散又收斂的線條，標著用完就丟](/figures/ge-two-diagrams.svg)

影片的 Demo 就是分工表最小的完整形狀：一個分派節點出發，同時展開三個子 agent 各自去讀三個開源專案（Godot、OBS、Home Assistant）的更新紀錄，最後一個合併節點等三邊都回報完，彙整成一張對照表。發散，再收斂。

![最小分工表：分派節點展開成三條並行線，各自讀一個專案的更新紀錄，最後收斂到合併節點；最慢的那條決定合併何時開始](/figures/ge-fan-out-merge.svg)

還有一個容易被標題騙的地方：Loop Engineering 沒有死。這幾個詞是一層一層往外疊的——最裡面 Context Engineering 管「模型這次看到什麼」，往外 Harness 管「agent 周圍有什麼工具和護欄」，再往外 Loop 管「單一 agent 怎麼跑完一輪」，最外面 Graph 管「多個 agent 怎麼接線」。圖上有五個節點，就有五個迴圈在跑，一個都沒少。

## 我自己的對照

我平常就是這樣工作的，只是從來沒把它叫成什麼 Engineering。我有一張很少動的組織圖：哪個 AI 常駐管研究、哪個管抓資料、哪個管寫程式、哪個只做第二意見，各自的規矩寫在一份文件裡，幾個月修一次。然後每接一個任務畫一張用完就丟的分工表：任務單寫好、拆給兩三條線並行跑、約好各自把產物放哪、最後我驗收合併。跟影片講的兩張圖一模一樣。

更有感的是影片講的「分工怎麼長出來」：一開始一個 agent 什麼都做，後來因為它每改一個東西就漏掉別的，才切出一個專門管那塊的。我的分工就是這樣試錯出來的，沒有人坐下來設計過——影片點名這正是常見的陷阱，動手前先花幾分鐘把分工寫下來，比出錯了再切便宜得多。

最後那個土方法值得單獨記：一個新詞紅了，先別急著讀文章，去翻幾個主要框架的 issue 和 PR——三個禮拜內沒有人因為這個詞改任何一行 code，它就只是個標籤，知道在講什麼就夠了。這比任何「要不要跟風」的焦慮都好用：讓行為當證據，不讓聲量當證據。

## 帶得走的一件事

我看完當天做了一件事，你也可以試：拿一張紙，寫下你手上每個 AI 工具各負責哪一塊——就算只用一個，也寫下它管什麼、你自己留什麼。我寫的時候卡了兩次，卡住的地方就是平常出錯的地方：兩個工具在做同一件事，出了錯不知道算誰的。寫得出來，你就有了自己的組織圖；寫不出來的那格，就是下次出錯的位置。
